# clash-smart-routing

> 给 **Clash Verge Rev** 加一层「会自己挑节点」的策略：按延迟自动择优、连接失败自动切换，
> 对 ChatGPT / GitHub / X 做专项处理，同时**保留手动钉某个国家 IP 的能力**。
>
> A profile-enhancement script for Clash Verge Rev (mihomo): turns select-only proxy groups into
> latency-aware ones with dedicated AI / GitHub / X handling, while keeping manual region pinning.

一个文件：`verge-script.js`。贴进 Verge 订阅卡片的「扩展脚本」即可，**不改订阅本体**，
机场更新订阅后会自动重新应用。

## 它解决什么问题

机场订阅给的策略组几乎都是 `type: select`——只有"手选"，没有"会挑"：

| 机场订阅默认 | 用了本脚本之后 |
|---|---|
| 所有流量压在一个手选节点上，节点一抖就得人去点 | 页面自动挑当前最快的节点，抖动时自动换 |
| 想按站点差异化（AI 要能过墙、GitHub 要快）只能全局共用一个节点 | AI / GitHub / 推特各走各的出口 |
| 想固定某个国家 IP，要在几十个节点里翻 | 一个地区组 + 一个"该地区最快"组 |
| 每次订阅更新，手工改的配置被冲掉 | 扩展脚本每次解析都重新注入，无需手工合并 |

## 策略组一览

脚本会在你的订阅之上**新建**这些组（原有组名不动，见「工作原理」）：

| 组 | 类型 | 说明 | 你需要手动介入吗 |
|---|---|---|---|
| 🚀 智能选择 | select | 总开关：自动组 / 专项组 / 各地区 | 很少 |
| ⚡ 测速优选 | url-test | 全部节点按延迟择优，`tolerance: 50` 迟滞防横跳 | 不 |
| 🛟 故障转移 | fallback | 连接失败立刻换下一个 | 不 |
| 🤖 AI 测速 | url-test | 以 `chatgpt.com/cdn-cgi/trace` 是否返回 **200** 为判据，只留真能过 GPT 的节点 | 不 |
| 🐙 GitHub | select | GitHub 专用出口，默认走测速优选 | 想钉死时 |
| 🐦 推特/X | select | 同上，并注入 6 条 X 域名规则 | 想钉死时 |
| 🇭🇰 香港 / 🇹🇼 台湾 / 🇯🇵 日本 / 🇸🇬 新加坡 / 🇺🇸 美国 / 🌍 其他地区 | select | 按地区分好的节点清单 | **想固定 IP 时** |
| ⚡ 美国优选 | url-test | 只在美国节点里挑最快的 | 不 |

## 前置条件

- 客户端：**Clash Verge Rev 2.x**（内核 `verge-mihomo` / mihomo），支持「扩展脚本」
- 订阅里的节点名带地区标识：`香港/台湾/日本/新加坡/美国` 或 `HK/TW/JP/SG/US`（正则见下）
- 不适用：Clash for Windows 原生版（没有扩展脚本机制）、Clash Verge 旧版 1.x、任何只吃静态配置的客户端

## 快速开始

**1. 复制脚本**
打开 `verge-script.js`，全选复制。

**2. 挂到订阅上**
Verge → 订阅页面 → 目标订阅卡片 → 「编辑」→ 找到「扩展脚本 / Script」→ 粘贴 → 保存。

**3. 启用**
- 主界面把模式切到 **规则**（`global` 模式下所有规则被绕过，新组完全用不上）
- 订阅卡片点「重新应用」（或重启 Verge）
- 「代理」页面顶部应出现 🚀 智能选择 / ⚡ 测速优选 / 🤖 AI 测速 … 等新组

**4. 让新默认值生效（只需一次）**
Verge 会记住你对每个组的手动选择（`profile.store-selected`）。若你以前把
`🔰国外流量` 这类组钉在某个节点上，新默认值不会自动生效——把对应组各点一次即可：

| 原有机场组（名字因机场而异） | 点成 |
|---|---|
| 走代理的主组（如 🔰国外流量 / PROXY / 节点选择） | ⚡ 测速优选 |
| 兜底组（如 ⚓️其他流量） | ⚡ 测速优选 |
| AI 组（如 🤖AI服务） | 🤖 AI 测速 |

做完之后就不用再管了。

## 日常用法

| 我想要 | 这么点 |
|---|---|
| 什么都不管，自动最快 | 不用点 |
| 美国 IP，但要好用的 | 🚀 智能选择 → 🇺🇸 美国 → ⚡ 美国优选 |
| 美国某个具体节点（要测某家银行/某站解锁） | 🚀 智能选择 → 🇺🇸 美国 → 具体节点 |
| 固定某个国家的 IP | 点对应地区组 → 点具体节点（会被记住） |
| ChatGPT 突然转圈 | 先看 🤖AI服务 是否被手动钉住，点回 🤖 AI 测速 |
| 某个网站要走直连 | 在 Verge 的「扩展配置 → 规则」里加一条 `DOMAIN-SUFFIX,example.com,DIRECT` |

## 工作原理

1. Verge 解析订阅后，把整份 config 交给扩展脚本的 `main(config, profileName)`。
2. 脚本按**节点名正则**把节点分成地区桶，剔除"剩余流量/到期时间/官网"这类信息节点。
3. 生成 url-test / fallback / select 组。已存在同名组则原地改写，**不产生重复组**（幂等）。
4. 在 `rules` 前面插入 GitHub / X 的规则；若你的机场兜底规则没落在被改造的组上，
   就把 `MATCH` 接到 🚀 智能选择（兜底是 `DIRECT`/`REJECT` 时不动，尊重原意）。
5. 返回 config，内核收到的是改造后的配置。

**为什么保留机场原有的组名**：订阅里通常有上千条规则指向 `🔰国外流量` 这类组。
新建组但不改这些引用，等于规则还是走在"手选组"上——所以脚本直接改造这些组：
**首项换成自动组，后面仍列出全部节点**，既能自动、又随时能手动钉死。

> **为什么一定要写 expected-status**：mihomo 的 url-test 默认只判断"这次探测有没有完成"，
> 不看返回码。一个已经挂了、但会立刻返回 503 的节点，反而比正常节点"响应更快"，会被顶到第一位。
> 加上 `expected-status` 之后，「快但坏」的节点会被判为不健康而剔除——
> 实测这台机器 59 个节点里有 18 个当时是死的，它们平时就是靠"秒回 503 所以延迟最低"在骗 url-test。

> 这也是本脚本用「扩展脚本」而不是「Merge」的原因：Merge 只能追加/覆盖整个字段，
> 改不动已有 select 组的成员列表与类型。

## 可调参数

都在 `verge-script.js` 顶部：

| 常量 | 默认 | 作用 |
|---|---|---|
| `TEST_URL` | `https://www.gstatic.com/generate_204` | 通用测速地址（204，最省流量） |
| `AI_TEST_URL` | `https://chatgpt.com/cdn-cgi/trace` | AI 组测速地址，用于判断"能不能过 OpenAI" |
| `INTERVAL` | `120` | 通用组测速间隔（秒） |
| `AI_INTERVAL` | `180` | AI 组测速间隔（秒） |
| `TOLERANCE` | `50` | 迟滞（毫秒）：新节点要快过 50ms 才切换，防止来回跳 |
| `TEST_EXPECTED` | `204` | 通用测速的期望状态码；不是 204（例如死节点秒回 503）即判为不健康 |
| `AI_EXPECTED` | `200` | AI 组的期望状态码；`chatgpt.com` 返回 200 才算"能过 GPT" |
| `JUNK` | 见源码 | 被排除的信息节点关键字正则 |
| `REGIONS` | 见源码 | 地区识别正则，按顺序匹配，先命中先算 |

常见改法：

- **机场组名不同**：改 `G.abroad / G.ai / G.other`。找不到就不改造，不影响新建组。
- **加一个新的地区组**：在 `regionPlan` 里加一行 `[G.ca, 'ca']`，并在 `REGIONS` 里加对应正则。
- **想给某个站单独建测速组**：照 `G.aiAuto` 的样子加一个 url-test 组，再把对应规则指过去。探测数会随组数上升，注意别把机场探测到限流。

## 验证

不自证，跑给你的内核看：

```bash
bash test/verify.sh
```

它会自动探测 Verge 数据目录与 `mihomo` / `verge-mihomo` 可执行文件（也可用
`VERGE_HOME` / `PROFILE` / `MIHOMO` 覆盖），然后：

1. 读你的当前订阅 → 跑扩展脚本
2. 断言：无重名组、无空组、无重复成员、成员全部存在、**无循环引用**、**每条规则的目标组都存在**
3. 用真实内核做 `mihomo -t` 语法校验
4. 回归用例：拿一份"组名完全不同"的模拟订阅（`test/fixtures/other-airport.yaml`），
   确认兜底规则被正确接管

依赖：`node` + `python3`（含 PyYAML）+ 一个 mihomo 内核。示例输出：

```
input: proxies=59 groups=5 rules=1275
after: groups=18 rules=1288
verdict: PASS
configuration file ... test is successful
MATCH 改写 -> MATCH,🚀 智能选择
```

## FAQ

**Q：全部节点同时显示 timeout？**
这是"全断"的特征，通常不是节点坏，而是**所有节点域名同时解析失败**。按顺序排查：

1. 解析任意一个节点域名（`nslookup <节点域名>`）：解析失败或返回可疑 IP → 换 DNS
2. 系统 DNS 改成 `119.29.29.29` + `223.5.5.5`，再 `Clear-DnsClientCache`
3. 客户端里点一次「测试延迟」——界面不会自动重测，会一直挂着旧值
4. 还是全红就别靠界面了：`python3 test/node-health.py <url> <expected>` 逐节点验证。注意区分两种故障：
   **全部超时**＝大概率解析/网络问题；**部分超时**＝机场侧节点死的（实测某机场 59 个节点里 23 个长期 503/504）


**Q：应用后新组是空的 / 只有两三个节点？**
节点名里没有可识别的地区标识。改 `REGIONS` 加你的机场的习惯写法（比如 `韩国|KR|首尔`）。

**Q：延迟全是红的 / 超时？**
测速地址被你所在的网络或机场拦了。换 `TEST_URL`，例如 `https://cp.cloudflare.com`。

**Q：🤖AI 组里的节点还是打不开 ChatGPT？**
① 看 🤖AI服务 是不是被你手动钉在某个节点上（要点回 🤖 AI 测速）；
② 有些机场的"AI 节点"实际落地在香港/新加坡中转，OpenAI 仍会拦——手动钉到 🇺🇸 美国 里的具体节点。

**Q：订阅更新后，我的手动选择还在吗？**
组名不变就还在（Verge 的 `store-selected` 按组名+节点名恢复）。机场改节点名会导致失效，重新点一次即可。

**Q：重启后策略组变回机场原样了？**
扩展脚本被解绑了——常见于重新导入订阅、Verge 大版本升级、或用别处备份覆盖了 `profiles.yaml`。重新粘贴脚本并「重新应用」。

**Q：脚本写错导致配置加载失败怎么办？**
清空该订阅卡片的「扩展脚本」→ 重新应用，立刻回到机场原版。Verge 的「日志」页能看到具体 JS 报错行。

**Q：会不会因为频繁测速被机场判定滥用？**
默认 58 个节点 × 120 秒 ≈ 每分钟一次探测，通常没问题。若收到限速/风控提示，把 `INTERVAL` 调到 `300`、`AI_INTERVAL` 调到 `600`。

**Q：为什么 GitHub / 推特没有各自的测速组？**
"延迟低"本质是"节点快"，复用 ⚡ 测速优选 已经达到目的，同时避免探测数翻几倍。
真要独立行为，按「可调参数」最后一条加组即可。

## 文件结构

```
verge-script.js                扩展脚本本体（贴进 Verge 用这一个文件就够）
test/verify.sh                 端到端校验：真实订阅 + 真实内核
test/run-script.mjs            断言脚本（12 项结构检查）
test/fixtures/                 异名机场回归用例
test/gpt-eligibility.py       节点体检：逐节点验证能不能过 GPT（需自起 mihomo REST API）
```

## 已知限制

- 只处理**按节点名识别地区**；机场若把节点叫 `节点1/节点2`，地区分组会退化成 🌍 其他地区
- AI 组不感知"落地 IP 归属"，只测 `chatgpt.com` 的可达性；个别中转节点会误判
- 依赖 Verge 的「扩展脚本」能力，客户端换生态后不能直接复用（但策略组结构可照抄）
